# 阶段一：项目探测、需求分析与设计

## 流程

1. 接收 `$ARGUMENTS`；确认或询问目标范围、用户目标、非目标、约束、`$DOC_PATH` 与可用验收标准。
2. 依照 `static/core/stance.md` 读取项目规范（仓库根与目标模块的 `AGENTS.md`/README，模块级优先）、构建文件、CI、迁移目录、测试目录和相邻功能。全栈探测至少覆盖：后端 `pom.xml`/`build.gradle`（Spring Boot 版本、starter、多模块 reactor）与 `application*.yml`/`properties`（数据源、中间件、端口）；前端 `package.json` 与 `vite.config`/`vue.config`（Vue 版本与构建工具、dev 代理、lint/test/build 脚本、状态管理与 UI 组件库依赖）。项目探测命中 `references/profiles/` 下某个项目 profile 时加载它，获得术语映射。记录已启用与未启用的 profile。
3. 启用 `frontend` profile 后确定 `$FRONTEND_ROOT`，检查 `$FRONTEND_ROOT/design-system/` 状态：完整目录只读并加载；目录不存在时加载 `static/fragments/design-system-init.md` 和 `references/templates/design-system/`，按条件前置流程处理；部分存在、包含用户内容或根目录不明确时标记 `blocked`，不得覆盖或猜测。生成位置固定为前端根目录下的 `design-system/`，且生成物只供 agent / 开发者参考，前端运行时代码不得引用。
4. 使用可用结构索引分析入口、相邻实现、调用方/被调用方与影响面；无索引时做只读降级分析并记录限制。
5. 输出下列项目事实；未知项保留 `unknown`：

| 类别 | 记录内容 |
|------|----------|
| 架构与目录 | 后端模块边界（单体/多模块 reactor、分层）、前端工程结构（views/components/api/store）、目标文件与可复用组件、`$FRONTEND_ROOT/design-system/` 状态 |
| 技术栈与构建 | Spring Boot 与构建工具（Maven/Gradle）、Vue 与构建工具（Vite/Webpack）、包管理、格式化、测试、构建与 CI 命令 |
| 用户体验/API | Vue 页面与路由（含菜单/权限入口来源：静态路由或后端下发）、组件库与状态管理、接口/事件、认证、错误与兼容性约定 |
| 数据与迁移 | 是否持久化、真实方言、ORM 映射（JPA 实体/MyBatis mapper）、数据变更策略（版本化迁移/启动初始化 SQL/手工 DBA 脚本/应用内任务）、数据量与回滚 |
| 集成 | 外部服务、SDK、消息、文件、AI 等依赖及失败策略 |
| 质量属性 | 权限、审计、隐私、日志、性能、并发、幂等、观测和发布风险 |

6. 对每项需求选择实际需要的实现区域：UI、API/契约、领域/业务逻辑、持久化、迁移、集成、异步处理、测试、文档。没有事实依据的区域写“不适用”，不要套 CRUD 或特定框架模板。
7. 对数据迁移、删除、权限、跨服务/模块契约等高风险项，若影响范围无法确认，建立 `blocked` 设计项并等待用户确认。

## 输出

1. **设计文档**：默认 `$DOC_PATH/$FILE_SLUG.html`；若项目文档惯例是 Markdown 或其他格式，则使用该惯例。
   - 按需读取 `references/templates/design-doc.html`。
   - 章节：需求概述、需求头脑风暴、数据模型设计（如适用）、业务流程、影响范围（含前端影响小节，如适用：页面/路由/菜单权限入口、组件与复用、API client 对接）、接口设计（如适用；每个接口除调用流程外，还需给出数据与中间件操作流程图：读/写/更新/删除/发布/消费）、模块拆分建议、非功能性需求、开发与验证建议。
   - 遵循模板顶部「填写原则」注释：大白话、表格每格一句话、未涉及章节整节删除、成品不残留 `{{...}}` 占位符与示例行。
   - 显示名、文件 slug、任务前缀必须分离；slug 仅包含小写字母、数字和连字符。
2. **Schema / 数据变更设计**：仅当功能涉及持久化且方言、数据变更策略已确认时生成。
   - 按项目实际数据变更策略落位（版本化 migration、启动初始化 SQL、功能目录自包含脚本或手工 DBA 流程）；没有版本化迁移工具时，说明执行主体、执行顺序与回滚记录方式；不要假定 `.sql` 文件路径或 SQL 方言。
   - 记录变更的前置状态、执行顺序、数据回填、回滚/恢复与兼容性。
3. **结构分析记录**：列出实际使用的工具，或降级分析的来源、限制和需要确认的结论。

## 确认关卡

```text
已完成项目探测与功能设计：
- 设计文档：<路径>
- 已启用 profile：<architecture / backend / frontend / database / ...>
- Schema / 数据变更：<路径或“不适用”>
- 结构分析：<工具结果或降级限制>
- 设计系统参考目录：<已存在并只读 / 已按模板生成 / blocked / 不适用>
- 设计系统输出：<$FRONTEND_ROOT/design-system/ 或“不适用”>
- 运行时引入：<无；设计系统只供 agent / 开发者参考>
- 阻塞项：<无 / 需确认事项>

请确认功能边界、影响范围、技术方案、设计系统参考目录处理和验收标准。
```

默认暂停等待用户确认后再进入任务拆分。`$AUTO_MODE=true` 时不暂停，按核心立场「确认关卡与自动模式」自检放行：输出上述摘要后追加「自动放行的假设清单」，高风险项保持 `blocked`，其余继续。
